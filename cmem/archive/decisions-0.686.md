# Decisions of the 0.686 work (archive)

Moved from `design-decisions.md` on 2026-11-19 (letter H38), verbatim, IDs kept. These governed
zailc's step-2 work on Fil-C 0.686 (the generators, the runtime builds, their oracles) or were
superseded: steps 2 and 3 are zilc's since 2026-10-27 (DD-31), and zailc is a clean slate since
2026-11-05 (DD-35). The 0.686 code they describe is still in the tree as history.

- **DD-03 · 2026-10-05** — 📌 **Zig 0.15.2, pinned, until zailc is proven to produce the same as zilc**
  (owner)
  *Why:* Zig 0.15.2 and Fil-C 0.686 share LLVM 20, so every translated piece can be checked against upstream's
  output on the same IR. Zig 0.16 emits LLVM 21 IR that Fil-C 0.686 cannot read; moving the line is a
  separate, later decision

- **DD-04 · 2026-10-08** — 🎯 **Order of work: step 2 before step 3, and inside step 2 the generators first**
  *Why:* The brief (`scope.md`) sizes step 2 as "~250k lines of C to build, almost none to write" and step 3
  as 25–35k lines of new Zig. Step 2's generators are the only *writing* in step 2, are deterministic and
  diffable, and prove the method (port, then prove byte-identity against the oracle) on something small before
  the pass

- **DD-05 · 2026-10-08** — 🔁 **Where upstream generates a file, zailc's generator reproduces it
  BYTE-IDENTICALLY, banner included**
  *Why:* The proof is a `cmp`. The generated banner therefore still reads `/* Generated by
  generate_pizlonated_forwarders.rb */` even though Zig wrote it; changing it would cost the byte-identity
  check for one line of vanity. Revisit only when zailc stops comparing against Ruby (i.e. when it owns the
  format)

- **DD-06 · 2026-10-08** — 📥 **Tables that are DATA upstream are imported mechanically, never transcribed**
  (`tools/gen/import-signatures.ts` → `src/gen/signatures.zig`)
  *Why:* 466 rows typed by hand would carry typos the SHA check would catch only as a whole; an importer makes
  an upstream change a re-run, and the import is itself reviewable (the tool is 90 lines). The generated file
  keeps upstream's licence notice because it is derived from upstream's file

- **DD-08 · 2026-10-08** — 📚 **`find_clang_include_dir.rb` is not ported.** `build.zig` passes Zig's own
  `lib/include` (the clang headers Zig ships) where libpas's Makefile uses the script's result
  *Why:* The script only locates the host clang's resource headers (`stddef.h`); Zig bundles the same headers
  and knows where they are (`zig env` → `lib_dir`). Porting a 54-line probe of `clang -###` would reintroduce
  a dependency on a host clang, the opposite of the goal. The brief says the same

- **DD-12 · 2026-10-08** — 🛠️ **Tools in Deno; build logic in `build.zig`; caches and outputs in
  `~/zailc-work`** (the Deno half SUPERSEDED 2026-10-22: Bun only, row below)
  *Why:* Owner rules carried from zilc (Deno or Bun, never Python or shell; the repo is on exFAT, so Zig's
  caches go to the Linux work area)

- **DD-13 · 2026-10-08** — 📂 **The Fil-C source tree is an INPUT of `zig build` (`-Dfilc-src`), read-only;
  nothing of it is vendored, and everything upstream generates in-tree (forwarders, `filc_native.h`, musl's
  headers) is generated into Zig's cache and reached through include paths**
  *Why:* The tree is the oracle's tree too; writing into it would taint the comparison and upstream's own
  build. Vendoring 250k lines would turn a translation project into a fork before the translation exists; a
  pinned tree plus mechanical importers (`signatures.zig`, `libpas_sources.zig`) keeps every upstream change a
  re-run. Later, `build.zig.zon` can fetch the pinned tree as a package (open question in zilc: whether a
  hash-checked source package counts as a "third-party download")

- **DD-14 · 2026-10-08** — 🎚️ **Compile settings are upstream's, expressed in Zig's terms**:
  `x86_64-linux-none` + `x86_64_v2` ↔ `-march=x86-64-v2 -nostdinc` with no libc from Zig; `ReleaseFast` + the
  explicit `-g -O3 -W -Werror -fno-strict-aliasing`; `pic = true`; `sanitize_c = .off`; `-isystem <zig
  lib>/include` for `find_clang_include_dir.rb`
  *Why:* Fidelity first: the objects must be the same translation units under the same configuration. Zig's
  defaults would otherwise add UBSan traps (Debug/ReleaseSafe) and its own libc headers; `-W -Werror` is kept
  on purpose, and Zig's clang 20.1.2 compiled all 178 objects clean under it

- **DD-15 · 2026-10-08** — 🔬 **Oracle level for compiled objects: the set of DEFINED global symbols per
  object must equal upstream's; undefined symbols are RATCHETED: each accepted difference is listed in
  `verify-libpas.ts` `KNOWN_UNDEF_DIFFS` with its `workarounds.md` entry, and a new or vanished one fails**
  (`verify-libpas.ts`; ratchet added 2026-10-08 at the owner's go, after the day-one review found that any
  number of undefined differences exited 0)
  *Why:* Bytes cannot match (upstream: Fil-C's clang 20.1.8 via its own driver; zailc: Zig's clang 20.1.2 via
  Zig's driver), and byte-level checks would measure the compiler, not the port. Equal defined-symbol sets
  prove the same files, same `#if` configuration and same visibility; behaviour is proven at the next level
  (link, run, trap; zilc's corpus and Fil-C's suite). One undefined-symbol difference exists today (W-4)

- **DD-16 · 2026-10-08** — 🎯 **The first release ships only when Fil-C is fully converted to Zig and verified
  against zilc's setups; the user installs Zig and ONLY Zig** (🔁 *superseded 2026-11-05: that conversion is
  zilc's track; zail's first release is `0.0.1`, the MVP, with nightlies before it — row below*) (owner: "Our
  first release of zailc will be after we have converted Fil-C fully to zig and verified against the zilc
  projects setups in place. I do not want to depend on their libraries. I wan[t] the user to use zig and only
  zig."). Nothing upstream-built ships, precompiled or vendored: not the release tarball's libraries, not
  Fil-C's clang. Both stay in the repo's tools as SCAFFOLDING and ORACLE only (tests, `link-run.ts`, the
  verify tools), and each piece of scaffolding is retired by a roadmap item. `v0.1.0` therefore waits for the
  rest of step 2 AND step 3 (the pass in Zig, which is what lets Zig compile the Fil-C-compiled pieces)
  *Why:* Closes the open "interim" row: shipping precompiled pieces is out, and Fil-C's clang inside `zig
  build` is acceptable only as a development bridge, never in a release. Enforced by the release gate (next
  rows)

- **DD-19 · 2026-10-09** — 🧮 **compiler-rt is built by Zig's clang with what compiler-rt's own CMake
  configures for it** (`zig build compiler-rt`; `tools/runtime/import-compiler-rt-sources.ts` runs CMake with
  build_compiler_rt.sh's options and `zig cc` in a scratch build dir and reads build.ninja)
  *Why:* Same rule as yolo musl: the flags and the source selection are upstream's build system's answer for
  OUR compiler. Upstream's release built it with GCC 11.4 (`.comment`). CMake's answer reproduces upstream's
  archive exactly (167 members, the same names, the same order) and adds `_Float16` support, which GCC 11
  lacked; that difference is an upstream defect (W-10) the owner chose to keep fixed (next row).
  crtbegin/crtend are CMake custom commands with no `-O` (so -O0) and no `-g`; the builtins are Release (no
  `-g`); the libc headers CMake's probes saw are glibc's, so Zig's glibc headers stand in

- **DD-21 · 2026-10-09** — 🧰 **yolo musl is built by Zig's clang with the flags musl's own configure picks
  for that compiler; libyoloc.a's members are its `.lo` (-fPIC) objects, as upstream's archive holds them**
  (`zig build yolomusl`; `tools/runtime/import-yolomusl-sources.ts` runs configure with `zig cc` in a scratch
  copy and evaluates the Makefile's object rules over the tree)
  *Why:* Upstream's release built yolo musl with **GCC 12.3** (the objects' `.comment` and `DW_AT_producer`),
  which zailc cannot use: only Zig. musl's configure is the upstream authority for the flags per compiler, so
  asking it about Zig's clang keeps the recipe upstream's. With `zig cc` it does not write `AOBJS = $(LOBJS)`
  (it does not detect PIC as the default, as it did for upstream's GCC). zailc keeps upstream's ARTIFACT shape
  instead, PIC members named as upstream's, because the release tarball is the oracle and the static-PIE link
  needs PIC anyway. The oracle level is libpas's (symbols) plus member ORDER, binding (strong/weak) and
  compile-unit names; the GCC-vs-clang residue is W-8, ratcheted

- **DD-22 · 2026-10-08** — 🔗 **Runtime behaviour oracle: the same Fil-C-compiled program, linked STATICALLY
  by the driver's own link line twice (upstream's runtime, then ours), must give identical output and exit
  code** (`tools/runtime/link-run.ts`, `tests/link/`)
  *Why:* Static because Fil-C's `libc.so` NEEDS `libpizlo.so`: a dynamic program would load upstream's runtime
  whatever it was linked against. The same command for both means the runtime is the only variable. Which
  runtime a binary got is proven from the link map: by member name for libpizlo (ours are unprefixed,
  upstream's `pas-pizlo-release-*`) and by hash where names coincide (`libyolounwind.a`). Only the panic's pid
  and ASLR addresses are normalised; the stock binary runs twice so self-variation is not reported as a
  difference
